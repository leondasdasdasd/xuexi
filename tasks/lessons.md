# 经验教训

- IMPORTANT: 用户说“和原章节管理逻辑保持一致”时，不能直接推断为“切回原接口”。本任务里用户明确纠正为当前基础设置页应继续走 mock 数据，只保持章节管理的数据组织逻辑和交互逻辑一致。
- YOU MUST: 涉及 mock 与接口切换时，必须先向用户确认数据来源；截图中出现登录超时或接口请求时，应优先怀疑错误接入了真实接口。
- IMPORTANT: 替换旧“章节管理/知识点管理”时，改动边界只覆盖这两个管理入口；“页面功能设置”属于独立原功能，必须保留原数据来源、保存逻辑和业务行为，不能因为去重 tab 或 mock 管理数据而覆盖。
- IMPORTANT: 基础设置章节/知识点管理里的教材版本必须调用 `/api/knowledge/getTeachingMaterial`，不要使用 `/api/question/teachingMaterialAndGrade/list` 作为版本来源；该接口返回单个默认版本对象，前端只展示这个当前版本。
- IMPORTANT: 章节管理绑定知识点只表达“关联了哪些知识点”，不需要主知识点/次知识点概念；后续不要在选择弹窗、标签展示或保存请求里新增主次标记。
- IMPORTANT: 知识点批量导入必须保留“增量更新”和“全量覆盖”两种方式；接入服务端接口时也要透传导入模式，不能只保留新增/更新语义。
- IMPORTANT: 基础设置页的知识点导入属于前后端联动能力；前端在 `question-test`，对应后端在上层目录 `/Users/xjl/IdeaProjects/teaching-task`，修改导入参数时必须同步检查两边契约。
- IMPORTANT: 数据分析“素养能力分析”列表新增“总分”时，取值必须来自“均分”所在单元格的上层素养模型 `questionScore` 字段，不能从 `columnDataModelList` 单元格模型取值。
- IMPORTANT: 跨分支移植提交时，必须按用户明确的业务范围筛选代码；如果提交中混有无关功能（例如智学网导入说明和校内外对比），只能移植目标业务相关代码，禁止把整次提交或无关 UI 一并复制。
- IMPORTANT: 校内外总分上线情况对比的分数线不能前端写死；不同考试分数线不同，必须来自用户导入、用户手动新增或服务端已保存数据，不能默认混入 730/720/710/700 等固定线。
- IMPORTANT: 校内外总分上线目标线允许 `>= 0` 的分数线，不能用 `>= 100` 这类前端阈值过滤用户表头；避免把小分制、等级映射或特殊分数线误判为无效列。
- IMPORTANT: 校内外对比导入的 AI 接入如果用户明确说“只有文本解析”，禁止扩展为图片上传、图片识别或多模态导入入口；AI 按钮只读取文本框内容并返回结构化草稿。
- IMPORTANT: 审查或修改前端逻辑时，必须主动检查学校/租户、学校 ID、分数线、阈值、权限开关、版本、默认参数、日期批次、兜底业务数据等写死值；会影响真实展示、过滤、权限、保存 payload、统计口径或接口请求的，必须作为风险点评估是否应由服务端、配置、用户输入或当前上下文动态提供。
- IMPORTANT: 校内外对比多校平均分不能用前端写死比例阈值（例如本校/外校均分相差 2.5 倍）覆盖成“需校验”；如果需要跨分制校验，应展示原始平均分并由服务端或可配置规则提供校验提示，不能吞掉接口或导入返回的数值。
- IMPORTANT: 校内外对比缺少良好率时不能由前端用及格率和优秀率推算；没有就是没有，应保持空值，若业务需要补齐必须来自服务端、用户导入或明确配置。
- IMPORTANT: 前端项目验证必须使用 `.nvmrc` 指定的 Node v16.20.2；如果 `nvm` 不存在，必须继续查找本机缓存或临时 Node 16 路径（例如 `/home/yungu/.cache/node16/node-v16.20.2-linux-x64/bin`），不能直接退到系统 Node 26 后把结果当作有效验证。
- IMPORTANT: 前端新增或调整第三方依赖、webpack alias、动态 import 或会进入生产包的新工具时，不能只跑 dev server；必须运行生产构建命令（本项目为 `npm run daily`）验证 UglifyJS/minify 阶段，避免 Jenkins 才暴露现代语法压缩失败。
- IMPORTANT: 提交给 AI 的成绩宽表不能直接使用空格对齐文本；调用前必须规范化为明确列分隔格式（优先 Tab 分隔），并在提示词中要求模型按列解析，避免把相邻列合并进同一个字段。
- IMPORTANT: 创建线上问题修复分支时，必须以用户明确指定的 `main` 为线上基线；不能仅凭 `origin/HEAD`、发布标签或既有分支历史推断线上分支。发现基线错误后，应从最新 `origin/main` 新建分支，并按业务差异精准迁移，避免整提交带入旧基线内容。
